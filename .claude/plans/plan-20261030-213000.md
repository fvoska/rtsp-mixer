# Plan: Make the macOS release build deterministic (Path A: ad-hoc signing)

Status: planned 2026-10-30, not started. Path B (Developer ID + notarization) is deferred, see the last section.

## Context

Findings from 2026-10-30:

- The Release build configuration of the Runner target uses `CODE_SIGN_STYLE = Automatic` with no `DEVELOPMENT_TEAM`. The outcome depends on the machine:
  - **CI (`macos-latest`)**: no signing identity exists, so Xcode falls back to ad-hoc signing and drops the entitlements. The job is green.
  - **Local Mac**: an `Apple Development` identity exists (team D4L9BUGPMF), so Xcode tries to use it and fails: `"Runner" has entitlements that require signing with a development certificate`.
- The published `rtsp-mixer-1.16.1-macos.dmg` was inspected with `codesign -dvv`: `Signature=adhoc`, `TeamIdentifier=not set`, **no entitlements at all**. `spctl -a -t exec` says `rejected`, so users get the Gatekeeper block today anyway.
- `macos/Runner/Release.entitlements` contains `app-sandbox`, `network.client` and a `keychain-access-groups` entry that names the stale bundle id `com.example.rtspAudioMixer` (the real one is `tech.voska.rtspMixer`). The keychain group is meaningless under ad-hoc signing.
- Without a keychain entitlement, `flutter_secure_storage` (v11.2, `flutter_secure_storage_darwin` 0.2.0) uses the data-protection keychain by default (`useDataProtectionKeyChain` defaults to `true` in the Swift plugin) and fails. `StorageService` (`lib/core/storage/storage_service.dart`) then switches to its in-memory fallback, so the released macOS app most likely loses the API key on every restart. Inferred from code, not observed on the released binary.
- The Debug configuration is fine and stays as it is: team D4L9BUGPMF, `RunnerDebug.entitlements` with `keychain-access-groups`, needs a Mac App Development provisioning profile. If `~/Library/Developer/Xcode/UserData/Provisioning Profiles/` is empty, run once from `macos/`: `xcodebuild -workspace Runner.xcworkspace -scheme Runner -configuration Debug -allowProvisioningUpdates build`.

Goal of Path A: the same ad-hoc result on every machine, a Release entitlements file that is true, and an API key that persists on macOS. Gatekeeper still shows the "unidentified developer" warning. That is accepted for now.

### 2. `macos/Runner/Release.entitlements`

Replace the content with only entitlements that work under ad-hoc signing:

```xml
<dict>
	<key>com.apple.security.network.client</key>
	<true/>
</dict>
```

Decisions baked in:

- **Remove `keychain-access-groups`.** Restricted entitlement, needs a provisioning profile, impossible with ad-hoc.
- **Remove `com.apple.security.app-sandbox`.** Ad-hoc Developer-ID-less distribution gains nothing from the sandbox, and the sandbox would need `com.apple.security.network.server` for the peer host (`lib/features/peer/services/peer_host_server.dart` binds an `HttpServer`) plus care around the PCM FIFO in `pcm_fifo.dart`. Keeping the sandbox is the alternative: then add `network.server` and test peer hosting and the level tap. Default choice for this plan: remove it.

`DebugProfile.entitlements` is referenced by the Profile config; it has `allow-jit` + `network.client` and is fine as it is.

### 3. `lib/core/storage/storage_service.dart`

Make secure storage use the legacy login keychain on macOS, which needs no entitlement:

```dart
static const _storage = FlutterSecureStorage(
  mOptions: MacOsOptions(useDataProtectionKeyChain: false),
);
```

Check the exact option class/field name against the installed `flutter_secure_storage` 11.2 Dart API (`MacOsOptions` and `useDataProtectionKeyChain` as the analyzer dictates). The Swift side reads `options["useDataProtectionKeyChain"]` and defaults to `true`, confirmed in `flutter_secure_storage_darwin-0.2.0/.../FlutterSecureStorageDarwinPlugin.swift:159`.

Side effects to be aware of:

- Debug builds on this Mac currently use the data-protection keychain with the keychain entitlement. After this change they use the login keychain too. Existing stored values (API key, selected cameras, `was_monitoring`) will look empty once, so the app behaves like a fresh install on the first debug run. Acceptable.
- The fresh-install marker logic in `StorageService` (wipe secure storage when `.install_marker` is missing) keeps working; login-keychain items also survive uninstall.
- Update the class doc comment (lines 10-15) to say macOS uses the login keychain and why.

### 4. `.github/workflows/release.yml`, job `build-macos`

After the `Build macOS app` step add a check so a signing regression fails the job instead of shipping:

```yaml
      - name: Verify code signature
        run: |
          APP="build/macos/Build/Products/Release/rtsp_mixer.app"
          codesign --verify --deep --strict --verbose=2 "$APP"
          codesign -d --entitlements :- "$APP"
```

The second command prints the entitlements into the log so the next audit does not need to download the DMG.

## Deferred: Path B, Developer ID + notarization

Not part of this plan. Keep for the day the DMG should install without the Gatekeeper block.

- Needs a paid Apple Developer Program membership (99 USD per year, shown in EUR at enrollment) where Filip is the Account Holder. Team D4L9BUGPMF is tied to the Infinum identity; a personal app should ship under a personal team.
- Create a "Developer ID Application" certificate (`.p12`) and an App Store Connect API key for `notarytool`. Store both as GitHub secrets (base64 `.p12`, its password, a temp keychain password, team id, API key id, issuer id, base64 `.p8`).
- Release config: `CODE_SIGN_IDENTITY = "Developer ID Application"`, `DEVELOPMENT_TEAM = <personal team>`, `ENABLE_HARDENED_RUNTIME = YES`. Then `keychain-access-groups` with `$(AppIdentifierPrefix)tech.voska.rtspMixer` can come back (Keychain Sharing is expected to work with Developer ID without a profile; verify on the first signed build) and `useDataProtectionKeyChain` can return to the default.
- CI: import the certificate into a temporary keychain, build, `codesign --verify --deep --strict`, create and sign the DMG, `xcrun notarytool submit --wait`, `xcrun stapler staple`, `spctl -a -t open --context context:primary-signature`.
- Risk: hardened runtime library validation vs. the media_kit libmpv dylibs. Xcode re-signs embedded frameworks, so it should pass; if the app dies at launch, add `com.apple.security.cs.disable-library-validation`.
- Path A steps 1 and 2 (manual signing, honest entitlements) are prerequisites for Path B as well, so nothing in this plan is throwaway.
